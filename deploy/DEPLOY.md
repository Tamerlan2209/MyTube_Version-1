# Развёртывание на VPS со своим доменом

Пошаговая инструкция для Ubuntu 22.04/24.04 VPS (Timeweb, REG.RU, Selectel,
Hetzner, DigitalOcean и т.п. — команды одинаковые везде). Если у тебя другой
дистрибутив — шаги те же, отличаются только команды установки пакетов.

## 0. Что нужно заранее

- VPS с Ubuntu и root/sudo-доступом (по SSH).
- Купленный домен, у которого в DNS можно добавить A-запись.

## 1. DNS

В панели управления доменом добавь A-запись:

```
Тип: A
Имя: @  (и второй записью — www)
Значение: IP-адрес твоего VPS
```

Изменения могут применяться от пары минут до нескольких часов.

## 2. Подключись к серверу и поставь Node.js

```bash
ssh root@ТВОЙ_IP

curl -fsSL https://deb.nodesource.com/setup_lts.x | sudo -E bash -
sudo apt install -y nodejs git
node -v
npm -v
```

## 3. Залей проект на сервер

Проще всего — через git (если положишь код в свой репозиторий) или просто
скопируй папку `MyTube` по SFTP/SCP:

```bash
scp -r ./MyTube root@ТВОЙ_IP:/opt/mytube
```

## 4. Установи зависимости и проверь, что сервер стартует

```bash
cd /opt/mytube/server
npm install
npm start
# должно появиться: MyTube запущен: http://localhost:3000
# останови Ctrl+C — дальше запустим через PM2, чтобы работало постоянно
```

## 5. PM2 — чтобы сервер работал постоянно и сам перезапускался

```bash
sudo npm install -g pm2
cd /opt/mytube
pm2 start deploy/ecosystem.config.js
pm2 save
pm2 startup
# pm2 покажет одну команду — скопируй и выполни её, чтобы сайт
# поднимался сам после перезагрузки сервера
```

Полезно:
```bash
pm2 status          # работает ли сервер
pm2 logs mytube       # логи в реальном времени
pm2 restart mytube    # после обновления кода
```

## 6. Nginx — обратный прокси + свой домен

```bash
sudo apt install -y nginx
sudo cp /opt/mytube/deploy/nginx-mytube.conf /etc/nginx/sites-available/mytube
sudo nano /etc/nginx/sites-available/mytube
# замени ТВОЙ_ДОМЕН.ру на реальный домен (два места в файле)
sudo ln -s /etc/nginx/sites-available/mytube /etc/nginx/sites-enabled/mytube
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx
```

Теперь `http://ТВОЙ_ДОМЕН.ру` должен показывать сайт.

## 7. HTTPS (обязательно для реального сайта)

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d ТВОЙ_ДОМЕН.ру -d www.ТВОЙ_ДОМЕН.ру
```

Certbot сам пропишет блок для 443/SSL и настроит редирект с http на https,
а также автопродление сертификата (проверь: `sudo certbot renew --dry-run`).

## 8. Файрвол

```bash
sudo ufw allow OpenSSH
sudo ufw allow "Nginx Full"
sudo ufw enable
```

Порт 3000 наружу открывать не нужно — снаружи виден только Nginx (80/443),
он сам проксирует на localhost:3000.

## 9. После деплоя — включи монетизацию

Зарегистрируй аккаунт с именем пользователя ровно **MyTube** (это единственный
аккаунт, для которого сайт откроет настройки) — под ним открой профиль →
блок «⚙️ Настройки сайта»:
- впиши ссылки на донат (Boosty/DonationAlerts/ЮMoney/PayPal/крипто);
- вставь код рекламного блока, если он у тебя есть (например, AdSense);
- впиши свой номер карты, имя получателя и цену за день размещения — это
  включит встроенный «Магазин рекламы»: любой посетитель сможет заказать
  рекламное место и оплатить его переводом, а ты будешь подтверждать оплату
  вручную в том же блоке настроек, во вкладке «Заявки на рекламу».

## 10. Обновление кода в будущем

```bash
cd /opt/mytube
# залей новые файлы (git pull или scp поверх)
cd server && npm install   # если появились новые зависимости
pm2 restart mytube
```

## Бэкапы

Все данные сайта — это папка `data/db.json` и папка `uploads/`. Периодически
копируй их куда-то ещё (на свой компьютер, в облачное хранилище) — если диск
VPS сломается, это единственное, что нельзя скачать заново.

```bash
tar -czf mytube-backup-$(date +%F).tar.gz -C /opt/mytube data uploads
```

## Развёртывание на Render (бесплатный тариф) — как не терять данные

Важно понимать: на бесплатном тарифе Render **вообще нельзя подключить
постоянный диск** — эта возможность есть только на платных тарифах
(от $7/мес). При этом бесплатный сервис «засыпает» после ~15 минут без
заходов и может быть пересоздан заново при следующем запуске — всё, что
лежало на локальном диске рядом с кодом (аккаунты, видео, база данных),
при этом стирается. Это ограничение самого хостинга, а не сайта.

Чтобы сайт оставался бесплатным и при этом ничего не терял, сервер умеет
хранить всё не на локальном диске, а в двух внешних бесплатных сервисах:

- **Upstash Redis** — база данных (аккаунты, видео-метаданные, комментарии,
  настройки сайта). Бесплатный тариф постоянный, без ограничения по времени.
- **Cloudinary** — сами файлы (загруженные видео и аватарки). Бесплатный
  тариф Cloudinary принимает видеофайлы весом до **100 МБ** за раз.

### Настройка Upstash Redis (база данных)

1. Зарегистрируйся на [upstash.com](https://upstash.com) (можно через
   GitHub/Google, бесплатно, без карты).
2. Создай новую Redis-базу (**Create Database**), регион — любой ближайший
   к серверу Render.
3. На странице базы найди раздел **REST API** — там будут две строки:
   `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN`.
4. В настройках сервиса на Render (**Environment**) добавь обе переменные
   с этими значениями.

### Настройка Cloudinary (файлы видео и аватарок)

1. Зарегистрируйся на [cloudinary.com](https://cloudinary.com) (бесплатно,
   без карты).
2. На главной странице консоли (**Dashboard**) найди строку **API
   Environment variable** — она выглядит как
   `CLOUDINARY_URL=cloudinary://123456789012345:AbCdEfGhIjKlMnOpQrStUvWxYz@your-cloud-name`.
3. Скопируй её целиком и добавь в **Environment** на Render как одну
   переменную с именем `CLOUDINARY_URL` (значение — то, что после знака `=`).

### После этого

Пересобери/перезапусти сервис на Render. В логах при старте появится
строка `база данных подключена к Upstash Redis` — значит всё подключилось
правильно. Теперь аккаунты, видео и комментарии переживут и «засыпание»,
и пересборку контейнера — потому что физически они больше не хранятся на
самом Render.

Если переменные `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` или
`CLOUDINARY_URL` не заданы, сервер продолжит работать как раньше — с
хранением на локальном диске — но тогда на бесплатном Render данные
по-прежнему будут теряться. Для VPS (раздел выше) эти переменные не нужны:
там диск постоянный сам по себе.

## Чтобы сайт не "засыпал" на Render (бесплатный тариф)

Бесплатный веб-сервис на Render останавливается после ~15 минут без входящих
HTTP-запросов, и первый заход после этого "будит" его 30-60 секунд. Ниже —
как этого избежать. Есть три уровня защиты; первый уже встроен в код, второй
нужно один раз включить вручную.

### 1) Встроенный self-ping (уже работает, ничего делать не нужно)

Сервер сам находит свой публичный адрес через переменную `RENDER_EXTERNAL_URL`
(Render подставляет её автоматически на любом плане, включая бесплатный) и
каждые 10 минут стучится сам на себя на лёгкий эндпоинт `/healthz`. В логах
после старта появится строка вида:

```
MyTube: keep-alive self-ping включён -> https://<твой-сервис>.onrender.com/healthz каждые 10 мин.
```

Это не требует настройки — просто задеплой обновлённый код.

### 2) Внешний "будильник" (рекомендуется — самый надёжный способ)

Self-ping не идеален: если процесс всё же уснёт или перезапустится в момент
между пингами, разбудить его некому. Поэтому дополнительно стоит подключить
бесплатный внешний сервис, который сам стучится на сайт снаружи каждые
5-10 минут:

- **UptimeRobot** ([uptimerobot.com](https://uptimerobot.com)) — регистрация
  бесплатно, без карты. Создай монитор: **Add New Monitor** → тип **HTTP(s)**
  → URL: `https://<твой-сервис>.onrender.com/healthz` → интервал **5 minutes**
  (минимум на бесплатном тарифе).
- Или **cron-job.org** — то же самое: указываешь URL `/healthz` и интервал
  запуска (например, каждые 10 минут).

Оба варианта заодно присылают уведомление на почту, если сайт всё-таки лёг —
удобно и как мониторинг "жив ли сайт" сам по себе.

### 3) Health Check Path в самом Render (ускоряет перезапуски и деплои)

В настройках сервиса на Render (**Settings → Health & Alerts → Health Check
Path**) укажи `/healthz`. Это не про "не давать уснуть", а про то, чтобы
Render считал деплой успешным только когда сервис реально отвечает, и
быстрее подхватывал перезапуск после сбоя.

### Важно понимать

- Всё это работает только пока сам процесс жив. Если Render положит сервис
  на плановое обслуживание или он упадёт по ошибке — оживит его либо внешний
  будильник (шаг 2, самый надёжный), либо следующий реальный посетитель.
- Бесплатный тариф Render даёт **750 часов/месяц** на аккаунт. Сервис,
  который не спит вообще, использует ~730-750 часов в месяц — укладывается
  в лимит для одного сервиса, но если на том же аккаунте есть и другие
  бесплатные сервисы, часы делятся между ними.
- 100%-ную гарантию "никогда не уснёт" даёт только платный тариф Render
  (от $7/мес, **Settings → Instance Type**) — там спин-дауна по
  неактивности вообще нет технически. Если сайт важен для реальных
  пользователей, а не только для теста — это самый надёжный вариант.
